## 5. PAYMENT-TO-ORDER CONTRACT

**NOWPayments identifies order by order_id** (orders.routes.js:950, nowpayments.routes.js:240)
- Order ID passed as string in NOWPayments API
- Webhook receives order_id, normalizes to integer
- Looks up order by id

**Validation:**
- User ownership checked before creating payment (orders.routes.js:755-760)
- Amount validation in webhook (nowpayments.routes.js:350-380) - compares reported price_amount to order.amount/order.price
- Currency validation

**Final payment statuses:** pending, submitted, verified, failed, refunded (normalized from NOWPayments statuses)

**Refund handling:** Webhook handles 'refunded' status, creates notification, updates order (doesn't revoke digital product access as no purchase records exist)

**Duplicate webhook handling:** Deduplicates order_events within 5 minutes by payment_id/purchase_id (nowpayments.routes.js:550-640)

**Multiple payment attempts:** Order has nowpayments_creating_lock to prevent concurrent creation. Can create new payment if previous not completed? Logic checks if payment_url exists and status is waiting/pending (orders.routes.js:810-870) and reuses it.

## 6. ARCHITECTURE COMPARISON

### Option A: Add digital_product_id to orders
**Pros:**
- Minimal schema change
- Fits existing single-item order model
- Easy to link in webhook
- Backend already handles package_id/service_id

**Cons:**
- Can't buy multiple digital products in one order
- Orders table becomes more heterogeneous
- Need to make package_id/service_id/digital_product_id mutually exclusive

### Option B: Introduce or reuse order_items
**Pros:**
- Proper normalization for multiple items
- Scalable
- Clean separation

**Cons:**
- Major refactor - no order_items exists
- Backend routes heavily assume single item
- Frontend would need changes
- More complex migration
- Breaking change to existing order flow

### Option C: Dedicated digital product checkout model linked to orders
**Pros:**
- Separate flow for digital products
- Less impact on existing order system
- Can have different logic

**Cons:**
- Duplicates checkout/payment logic
- More complex to maintain
- Unclear how it integrates

---

## 7. RECOMMENDED APPROACH

**Recommendation: Option A - Add digital_product_id to orders**

**Justification:**
1. **Fits existing model** - Orders already handle single items (package OR service). Digital product is also a single item.
2. **Minimal changes** - Add column, update order creation logic, update webhook to create purchase records
3. **Backend compatibility** - Orders routes already have pattern for package_id/service_id, can extend it
4. **Frontend** - Can adapt existing checkout flow or create simple flow
5. **No breaking changes to packages/services** - Existing functionality unchanged
6. **Fastest path to fix the gap** - Purchase creation can be added in webhook using digital_product_id from order

**Required changes:**
- Migration: Add digital_product_id to orders (FK to digital_products, nullable), make mutually exclusive with package_id/service_id
- Orders route: Accept digital_product_id, validate it exists and is active, create order with digital_product_id
- Webhook: When order has digital_product_id and payment verified, create/update digital_product_purchases record
- Digital products download already checks purchases - will work once purchases created

**Alternative consideration:** If future requirement is to sell multiple digital products together, would need to migrate to order_items, but current evidence shows single-item model and no UI for cart.
